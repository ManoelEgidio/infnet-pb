1. Introdução e Visão Geral da Arquitetura em Produção

Esta etapa consolida a evolução arquitetural realizada ao longo do semestre no sistema TaskManager PB. A aplicação, que teve sua modularização iniciada com monólito e microsserviços síncronos (TP1-TP3) e foi transformada em uma arquitetura orientada a eventos assíncrona com RabbitMQ (TP4), é agora totalmente preparada para operação em escala no ambiente de produção (TP5).

A solução adota os paradigmas fundamentais de sistemas Cloud-Native modernos:

  • Imutabilidade de Infraestrutura: Conteinerização com imagens Docker mínimas geradas via Multi-Stage Build, isolando ambiente de compilação do runtime de produção.
  • Orquestração e Alta Disponibilidade: Especificação de topologia completa em Kubernetes (K8s), com Rolling Updates sem indisponibilidade (Zero Downtime), auto-escalonamento horizontal (Horizontal Pod Autoscaler - HPA) baseado em demanda de CPU, e isolamento em namespace dedicado (taskmanager-prod).
  • Observabilidade Tridimensional: Implementação dos três pilares da observabilidade: Logs Estruturados com identificadores de correlação (traceId e spanId); Métricas expostas no formato aberto Prometheus (Spring Boot Actuator); Rastreamento Distribuído (Distributed Tracing) de ponta a ponta com Micrometer Tracing Brave e OpenZipkin.
  • Automação CI/CD: Pipeline automatizado via GitHub Actions executando análise estática, suítes de testes, build das imagens Docker e validação estrita de esquemas Kubernetes com Kubeconform e Kind.

2. Conteinerização com Docker (Item 1 e 7 da Rubrica)

Para garantir portabilidade, segurança e eficiência de recursos, todos os componentes do sistema foram conteinerizados utilizando a técnica de Multi-Stage Builds.

2.1 Microsserviços Backend (Java 21 / Spring Boot 3.4)

Os Dockerfiles do task-service e notification-service empregam um estágio construtor baseado no eclipse-temurin:21-jdk-alpine para compilação e empacotamento com Gradle, e um estágio final de produção enxuto com eclipse-temurin:21-jre-alpine.

Diretrizes de Segurança e Otimização Aplicadas:

  • Princípio do Menor Privilégio: Execução sob usuário não-root (appuser / appgroup), eliminando riscos de escalada de privilégios.
  • Healthcheck Nativo do Container: Sondagem periódica ao endpoint de liveness do Spring Boot Actuator (/actuator/health/liveness) para supervisão pelo daemon do Docker.
  • Otimização de JVM em Containers: Definição de flags de memória adequadas a contêineres (-Xms256m -Xmx512m -XX:+UseG1GC).
# Exemplo do Dockerfile Multi-Stage (task-service)
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /workspace
COPY gradlew . && COPY gradle gradle && COPY build.gradle settings.gradle ./
RUN chmod +x gradlew && ./gradlew dependencies --no-daemon || true
COPY src src
RUN ./gradlew bootJar -x test --no-daemon

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
COPY --from=builder /workspace/build/libs/*.jar app.jar
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s --start-period=40s \
  CMD wget --quiet --tries=1 --spider http://localhost:8080/actuator/health/liveness || exit 1
ENV SPRING_PROFILES_ACTIVE=prod
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]

3.1 Estratégia de Atualização RollingUpdate (Zero Downtime)

Para viabilizar entregas contínuas em produção sem indisponibilidade para o usuário, os deployments foram configurados com: 

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1        # Permite criar 1 pod excedente durante o deploy
    maxUnavailable: 0  # Nenhum pod existente é encerrado antes do novo estar Ready

3.2 Escalabilidade Automática com Horizontal Pod Autoscaler (HPA)

Para garantir a elasticidade do sistema perante variações de carga de trabalho (como rajadas de mensagens ou altas taxas de criação de tarefas), foram configurados HPAs para ambos os microsserviços: 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: task-service-hpa
  namespace: taskmanager-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: task-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Quando a utilização média de CPU ultrapassar 70%, o control plane do Kubernetes aloca automaticamente réplicas adicionais até o teto de 10 pods, reduzindo a contagem para o mínimo de 2 pods quando a demanda normalizar.

4. Observabilidade, Monitoramento e Tracing (Item 3 da Rubrica)

A operação em produção exige visibilidade em tempo real do estado interno dos serviços:

4.1 Liveness e Readiness Probes no Kubernetes

O Spring Boot Actuator foi configurado com management.endpoint.health.probes.enabled=true, expondo os endpoints dedicados para o ciclo de vida dos contêineres:

  • Liveness Probe (/actuator/health/liveness): Indica se a aplicação Java e a JVM estão saudáveis. Se falhar, o Kubernetes reinicia o pod automaticamente.
  • Readiness Probe (/actuator/health/readiness): Indica se a aplicação está pronta para receber requisições de clientes (banco de dados conectado, broker RabbitMQ acessível). Se falhar, o pod é removido temporariamente do balanceamento de carga do Service.

4.2 Agregação de Métricas com Prometheus

Ambos os microsserviços utilizam o Micrometer Prometheus Registry para disponibilizar métricas no padrão aberto via endpoint /actuator/prometheus. O servidor Prometheus central realiza o scraping a cada 5 segundos, coletando:

  • Latência de requisições HTTP por rota e código de resposta (http_server_requests_seconds);
  • Consumo de memória Heap e Non-Heap da JVM (jvm_memory_used_bytes);
  • Uso de CPU da máquina e do processo (process_cpu_usage);
  • Contadores de mensagens AMQP processadas e taxas de erro (rabbitmq_consumed_total).

4.3 Rastreamento Distribuído (Distributed Tracing com Zipkin)

Foi implementado o rastreamento ponta a ponta com Micrometer Tracing Bridge Brave e Zipkin Reporter. Cada transação recebe um traceId exclusivo que é propagado entre os microsserviços via cabeçalhos HTTP e metadados AMQP do RabbitMQ:

  • Trace Context Injection: O task-service cria o traceId no recebimento da requisição HTTP e o injeta nas propriedades da mensagem RabbitMQ ao publicar o evento.
  • Trace Context Extraction: O notification-service extrai o mesmo traceId ao consumir a mensagem da fila, permitindo visualizar a jornada completa da transação no console do Zipkin (http://localhost:9411).
  • Correlação em Logs Estruturados: O padrão de log do Spring foi formatado para incluir o contexto de tracing: %5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}].

5. Gestão de Configuração e Versionamento (Item 4 da Rubrica)

O projeto adota rígidas práticas de gestão de configuração e controle de versão:

  • Segregação Estrita de Ambientes: Configuração baseada em perfis Spring: application.properties para desenvolvimento local com banco em memória e RabbitMQ local; application-prod.properties para ambiente de contêineres e Kubernetes, lendo valores dinâmicos de variáveis de ambiente.
  • Injeção por Variáveis de Ambiente: Valores como RABBITMQ_HOST, RABBITMQ_PORT, RABBITMQ_USERNAME e ZIPKIN_ENDPOINT utilizam fallbacks (ex: ${RABBITMQ_HOST:localhost}), permitindo que o mesmo código execute tanto nativamente quanto no cluster K8s.
  • Higiene de Versionamento com Git: Configuração criteriosa do arquivo .gitignore em todos os módulos, prevenindo o commit acidental de binários (*.jar, build/, dist/), dependências externas (node_modules/, .gradle/) e relatórios transitórios.
