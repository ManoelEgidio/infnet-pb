1. Introdução

Esta etapa representa a fase de transição da aplicação TaskManager PB para a operação em ambiente de produção simulado. O foco central consistiu em conferir estabilidade, escalabilidade, segurança e manutenibilidade ao ecossistema distribuído através de conteinerização com Docker, orquestração elástica com Kubernetes, monitoramento tridimensional com Spring Boot Actuator, Prometheus e Zipkin, e automação do ciclo de vida com GitHub Actions.

2. Subcompetência 1: Implantação com Docker (Conteinerização Multi-Stage)

Todos os componentes do sistema foram conteinerizados adotando a estratégia de compilação multiestágio (Multi-Stage Builds), que separa o ambiente pesado de compilação da imagem final mínima executada em produção:

  • task-service e notification-service: Estágio 1 construtor baseado em eclipse-temurin:21-jdk-alpine compilando via Gradle; Estágio 2 de runtime enxuto baseado em eclipse-temurin:21-jre-alpine. A execução é configurada sob usuário não-privilegiado (appuser / appgroup) para mitigação de riscos de segurança. Os contêineres possuem verificação de integridade nativa (HEALTHCHECK) consultando a liveness probe do Spring Boot Actuator (/actuator/health/liveness).
  • frontend: Estágio 1 construtor com oven/bun:alpine para compilação do bundle estático (Vite); Estágio 2 com nginx:alpine servindo o Single Page Application com compressão Gzip e reverse proxy para os microsserviços.
  • Orquestração com Docker Compose: O arquivo docker-compose.prod.yml orquestra todos os serviços (task-service, notification-service, frontend, rabbitmq, zipkin e prometheus) em rede isolada taskmanager-network com ordenação de inicialização baseada na integridade dos serviços.

3. Subcompetência 2: Orquestração e Escalabilidade com Kubernetes

Para gerenciar o ciclo de vida dos contêineres em produção, foi desenvolvida a especificação declarativa completa no diretório TP5/k8s/:

  • 00-namespace.yaml: Cria o namespace isolado taskmanager-prod para separação lógica e controle de governança.
  • 01-configmap.yaml e 02-secrets.yaml: Segregação entre configurações públicas e credenciais criptografadas em Base64 do broker RabbitMQ.
  • 10-rabbitmq.yaml, 11-zipkin.yaml e 12-prometheus.yaml: Deployments e Services ClusterIP para suporte à mensageria, rastreamento e coleta de métricas.
  • 20-task-service.yaml e 21-notification-service.yaml: Deployments com 2 réplicas mínimas, estratégia RollingUpdate (maxSurge=1, maxUnavailable=0 para deploy sem indisponibilidade), cotas de recursos (requests/limits de CPU e memória) e probes de liveness e readiness.
  • Horizontal Pod Autoscaler (HPA): Configurado para ambos os microsserviços com auto-escalonamento de 2 a 10 réplicas baseado em utilização de CPU acima de 70%.
  • 30-frontend.yaml e 40-ingress.yaml: Deployment da interface com Service NodePort (porta 30080) e Ingress unificado para roteamento de tráfego.

4. Subcompetência 3: Monitoramento de Microsserviços (Observabilidade, Logs e Tracing)

A solução contempla os três pilares da observabilidade para monitoramento contínuo:

  • Probes de Ciclo de Vida: Configuração do Spring Boot Actuator expondo /actuator/health/liveness (verificação de saúde para reinicialização do pod) e /actuator/health/readiness (verificação de prontidão para recepção de requisições de clientes).
  • Métricas Abertas (Prometheus): Exportação de métricas padronizadas no endpoint /actuator/prometheus, coletadas periodicamente pelo Prometheus Server (porta 9090).
  • Rastreamento de Transações (Distributed Tracing): Instrumentação com Micrometer Tracing Brave e envio de spans ao OpenZipkin (porta 9411). Cada requisição HTTP gera um traceId exclusivo que é propagado nos metadados AMQP das mensagens publicadas no RabbitMQ, viabilizando o rastreamento da jornada ponta a ponta da transação no console do Zipkin.
  • Logs Estruturados com Correlação: O formato de log do Spring Boot inclui o identificador do serviço, o traceId e o spanId: %5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}].

5. Subcompetência 4: Controle de Versão e Gestão de Configuração

A separação entre ambientes de desenvolvimento e produção é garantida por perfis Spring:

  • application.properties: Perfil padrão de desenvolvimento com H2 local e fallback para RabbitMQ local.
  • application-prod.properties: Perfil de produção ativado por SPRING_PROFILES_ACTIVE=prod, consumindo variáveis dinâmicas injetadas pelo Kubernetes ConfigMap e Secret (RABBITMQ_HOST, RABBITMQ_PORT, ZIPKIN_ENDPOINT).
  • Controle de Versão: O repositório Git mantém histórico claro de mudanças, com arquivos .gitignore configurados para impedir o commit de artefatos de build, binários e relatórios intermediários.

6. Subcompetência 5: Automação CI/CD com GitHub Actions

A automação do fluxo de integração e entrega contínua foi implementada no workflow .github/workflows/ci-cd-tp5.yml, estruturado em quatro etapas:

  • Backend CI: Matriz paralela para task-service e notification-service executando testes automatizados, build com Gradle (bootJar) e publicação de relatórios JUnit.
  • Frontend CI: Instalação limpa com Bun, verificação estática com Oxlint e compilação do bundle de produção com Vite.
  • Docker Build: Compilação das imagens multi-stage dos microsserviços e frontend.
  • K8s Validation & CD Simulation: Validação de sintaxe e schemas com kubeconform e implantação automatizada em cluster simulado Kind.

7. Subcompetência 6: Suíte de Testes Abrangentes

Ambos os microsserviços possuem suítes de testes automatizados que cobrem múltiplos aspectos do sistema distribuído:

  • Testes unitários e de integração de serviços e regras de negócio.
  • Testes de repositórios JPA e persistência relacional.
  • Testes de publicação e consumo de mensagens RabbitMQ nas exchanges Direct, Topic e Fanout, além de roteamento para DLQ.
  • Testes de observabilidade (ActuatorObservabilityIntegrationTest) validando status UP na liveness probe, readiness probe e endpoint de métricas Prometheus.

Todos os testes foram executados com 100% de sucesso.

8. Subcompetência 7: Apresentação da Operação no Frontend

O frontend React conta com ferramentas integradas para demonstração e supervisão da operação:

  • Painel de Observabilidade (Modal): Permite verificar em tempo real o estado de UP/DOWN das probes de liveness e readiness de cada microsserviço, além de links diretos para a interface de telemetria do Zipkin e métricas do Prometheus.
  • Indicadores de Status na Navbar: Pílulas de monitoramento exibindo a conectividade com o task-service (:8080), notification-service (:8082) e RabbitMQ (:5672).

10. Conclusão

A etapa final consolidou com sucesso a maturidade operacional do TaskManager PB. O sistema está preparado para operar em produção, dotado de escalabilidade automática horizontal via Kubernetes, isolamento de contêineres com Docker, monitoramento contínuo com Prometheus e Zipkin, testes automatizados e esteira de CI/CD via GitHub Actions.
