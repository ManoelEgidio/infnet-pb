Relatório Técnico - Criação e Integração de Microsserviço (TP3)

Aluno: Manoel Egidio | Entrega: Terceira Etapa (TP3)

1. Introdução

Este relatório documenta a evolução da aplicação TaskManager PB da sua arquitetura monolítica para uma arquitetura distribuída baseada em microsserviços. O objetivo central desta etapa consistiu na separação de responsabilidades e desacoplamento do domínio de Notificações, criando um microsserviço autônomo e integrando-o ao serviço principal de tarefas por meio de comunicação RESTful utilizando Spring Boot e Spring Cloud OpenFeign.

2. Atualização do Modelo de Domínio

Seguindo as diretrizes do Domain-Driven Design (DDD), o modelo de domínio do sistema foi refinado para isolar o bounded context de Notificações em relação ao bounded context de Gestão de Tarefas:

  • Bounded Context Gestão de Tarefas (task-service): Mantém o agregado Task, Category e TaskHistory. Este serviço atua como consumidor do serviço de notificações, delegando os alertas operacionais.
  • Bounded Context de Notificações (notification-service): Microsserviço independente com base de dados própria (H2 em memória: notificationdb), responsável pelo ciclo de vida das entidades Notification, canais de entrega (IN_APP, EMAIL, SMS) e tipos de eventos (TASK_CREATED, TASK_STATUS_CHANGED, TASK_DELETED).

3. Criação de Endpoints da API REST

Foram implementados novos contratos e endpoints RESTful para viabilizar as operações do novo microsserviço na porta 8082:

  • POST /api/notifications: Cria e armazena uma nova notificação com base no DTO de requisição validado.
  • GET /api/notifications: Consulta a listagem de notificações com suporte a filtros por destinatário e status de leitura.
  • GET /api/notifications/summary: Retorna o total de notificações, contagem de pendentes e última atualização para o painel de interface.
  • PATCH /api/notifications/{id}/read: Atualiza o estado da notificação para lida com registro do instante de leitura.
  • PATCH /api/notifications/read-all: Marca em lote todas as notificações pendentes de um destinatário.

4. Implementação de Microsserviço com Spring Boot e Spring Cloud

A implementação dos microsserviços utilizou o ecossistema Spring:

  • Spring Boot 3.4.3: Inicialização simplificada com autoconfiguração e gestão de dependências via Gradle.
  • Spring Cloud OpenFeign: No task-service, foi configurada a interface declarativa NotificationClient. Toda vez que uma tarefa é criada, concluída ou removida, o cliente Feign dispara chamadas HTTP assíncronas para o microsserviço de notificações.
  • Mecanismo de Fallback (Resiliência): Implementação da classe NotificationClientFallback. Caso o notification-service esteja temporariamente indisponível ou ocorra falha de rede, a falha é degradada graciosamente com log de aviso, sem comprometer o fluxo principal de persistência das tarefas.

5. Expansão da Cobertura de Testes Automatizados

A suíte de testes foi ampliada em ambos os microsserviços, cobrindo testes unitários, testes de integração de repositórios JPA e validação de contratos de API com MockMvc:

  • TaskManagerApplicationTests (task-service): Ciclo de vida completo das tarefas, persistência e auditoria.
  • TaskHistoryRepositoryTest (task-service): Consultas ordenadas e integridade relacional.
  • NotificationServiceTest (notification-service): Regras de negócio, contadores e filtros de leitura.
  • NotificationControllerTest (notification-service): Validação de requisições HTTP, paginação e status codes.
  • NotificationRepositoryTest (notification-service): Queries customizadas por destinatário e contagem de não lidas.

Todos os 18 testes automatizados foram executados e aprovados com 100% de sucesso.

6. Componentes da Interface de Usuário (React)

O frontend React foi adaptado para consumir os dois microsserviços:

  • Central de Notificações (Drawer): Painel lateral com badge dinâmico de notificações não lidas, listagem ordenada, opção de marcar individualmente como lida ou limpar todas em lote.
  • Indicador de Saúde dos Serviços (Navbar): Monitor em tempo real verificando a disponibilidade do task-service (:8080) e do notification-service (:8082) com polling a cada 8 segundos.

8. Conclusão

A terceira etapa consolidou a transição da aplicação para a arquitetura orientada a serviços distribuídos. A segregação do domínio de notificações permitiu avaliar na prática o desacoplamento de responsabilidades, os benefícios do desenvolvimento independente por serviço e os padrões de resiliência necessários na comunicação distribuída.
