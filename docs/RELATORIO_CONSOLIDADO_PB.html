1. Introdução e Visão Geral da Solução

Este relatório consolida a totalidade do trabalho prático desenvolvido ao longo do bloco de Engenharia de Softwares Escaláveis. O projeto, denominado TaskManager PB, foi concebido e evoluído segundo um processo ágil, incremental e iterativo, partindo de um monólito simples e avançando progressivamente até atingir uma arquitetura corporativa distribuída, orientada a eventos e pronta para operação em ambiente de produção em nuvem.

A trajetória de desenvolvimento abrangeu cinco etapas complementares:

  1. Etapa 1 (TP1): Construção do monólito base com Spring Boot 3, arquitetura em camadas, princípios DDD e interface web em React.
  2. Etapa 2 (TP2): Modelagem e implementação da camada de persistência relacional com Spring Data JPA, mapeamento ORM e subsistema de auditoria de histórico.
  3. Etapa 3 (TP3): Decomposição arquitetural com a introdução do microsserviço de notificações e integração síncrona via Spring Cloud OpenFeign com fallback resiliente.
  4. Etapa 4 (TP4): Refatoração para Arquitetura Orientada a Eventos (EDA) utilizando o RabbitMQ como message broker assíncrono (exchanges Direct, Topic, Fanout e DLQ).
  5. Etapa 5 (TP5): Preparação para operação em produção com conteinerização Docker multiestágio, orquestração elástica com Kubernetes (HPA de 2 a 10 pods), observabilidade (Actuator Probes, Prometheus, Zipkin Tracing) e esteira automatizada de CI/CD com GitHub Actions.

2. Etapa 1: Construção do Monólito com Spring Boot

Na etapa inicial, foi estruturado o núcleo do sistema de gerenciamento de tarefas seguindo boas práticas de engenharia de software:

  • Design em Camadas: Separação rígida de responsabilidades em controladores (camada de apresentação REST), serviços (regras de negócio e orquestração) e repositórios (abstração de acesso a dados).
  • Autoconfiguração e Gestão de Dependências: Uso do Spring Boot 3.4 com starter dependencies gerenciadas via Gradle, eliminando configurações manuais redundantes e preparando o projeto para manutenibilidade.
  • APIs RESTful com Spring MVC: Exposição de endpoints HTTP com métodos semânticos (GET, POST, PUT, PATCH, DELETE), DTOs validados via Bean Validation (@NotNull, @NotBlank, @Future) e tratamento centralizado de exceções com @RestControllerAdvice.
  • Princípios SOLID e Clean Code: Inversão de dependência mediante injeção por construtor, classes com responsabilidade única e desacoplamento de contratos.
  • Domain-Driven Design (DDD): Identificação do domínio central (Core Domain) de Gestão de Tarefas, Value Objects para invariantes de negócio (como prioridades HIGH/MEDIUM/LOW e status PENDING/IN_PROGRESS/COMPLETED) e separação de bounded contexts.
  • Interface React: Desenvolvimento de Single Page Application (SPA) para consumo das APIs REST, proporcionando gerenciamento interativo de tarefas e métricas.

3. Etapa 2: Camada de Persistência com JPA e Spring Data

A segunda etapa substituiu coleções voláteis em memória por uma camada de persistência relacional robusta com Spring Data JPA e banco de dados H2:

  • Mapeamento Objeto-Relacional (ORM): Aplicação criteriosa das anotações JPA (@Entity, @Table, @Id, @GeneratedValue, @Column, @Enumerated) nas entidades de domínio Task, Category e TaskHistory.
  • Relacionamentos e Isolamento: Modelagem de relacionamentos @ManyToOne com carregamento preguiçoso (FetchType.LAZY) entre tarefas e categorias, assegurando isolamento de agregados e prevenindo o problema de consultas N+1.
  • Repositórios Spring Data: Criação de interfaces estendendo JpaRepository, aproveitando derived query methods e consultas customizadas em JPQL para buscas por status, prioridade e categoria.
  • Controle Transacional e Integridade: Uso de @Transactional em operações de escrita no serviço para garantir atomicidade, consistência e rollback automático em falhas.
  • Histórico de Mudanças e Auditoria: Implementação da entidade TaskHistory registrando todas as transições de estado, alterações de dados, autor da modificação e timestamp, com endpoint dedicado para consulta cronológica de auditoria.

4. Etapa 3: Microsserviço com Spring Boot e Spring Cloud

A terceira etapa realizou a primeira quebra arquitetural do monólito para introduzir o microsserviço independente de notificações:

  • Segregação de Responsabilidades: O bounded context de Notificações foi isolado no notification-service (porta 8082), com sua própria base de dados em memória (notificationdb), desacoplado do task-service (porta 8080).
  • Endpoints REST do Microsserviço: Implementação de endpoints para cadastro de alertas, listagem filtrada por destinatário, contadores de mensagens não lidas e atualização de status de leitura.
  • Spring Cloud OpenFeign e Resiliência: No task-service, foi configurada a interface NotificationClient para acionamento HTTP declarativo do serviço de notificações. Para garantir que o sistema não falhasse em cascata caso o serviço remoto estivesse indisponível, foi implementado o padrão de fallback (NotificationClientFallback), fornecendo degradação graciosa.
  • Cobertura de Testes: Ampliação das suítes de testes com 18 testes automatizados aprovados, cobrindo controllers, serviços e repositórios de ambos os serviços.
  • Interface do Usuário: Inclusão da Central de Notificações em painel lateral deslizante (Drawer) e pílulas de status verificando a integridade dos serviços em tempo real.

5. Etapa 4: Refatoração para Arquitetura Orientada a Eventos (EDA)

A quarta etapa modernizou a comunicação entre microsserviços, substituindo as chamadas HTTP síncronas por mensageria assíncrona orientada a eventos com RabbitMQ:

  • Avaliação de Trade-offs (Prós e Contras): Demonstração de que o desacoplamento temporal, o amortecimento de picos de carga (load leveling) e a tolerância a falhas justificam a complexidade adicional inerente ao modelo de consistência eventual e rastreamento distribuído.
  • Padrões de Mensagens Desenvolvidos:
    • Direct Exchange: Roteamento ponto a ponto com chave exata para eventos transacionais de criação, alteração e exclusão de tarefas.
    • Topic Exchange: Roteamento seletivo com chaves padronizadas (task.priority.*) para direcionamento de tarefas urgentes à fila de alta prioridade.
    • Fanout Exchange: Difusão em broadcast para comunicados sistêmicos operacionais direcionados a todos os usuários.
    • Dead Letter Queue (DLQ): Roteamento automático de mensagens com erro irrecuperável ou rejeitadas após 3 tentativas com backoff exponencial para análise e reprocessamento posterior.
  • Abstrações Spring AMQP: Uso de RabbitTemplate para publicação não bloqueante e anotações @RabbitListener nos consumidores, com serialização JSON padronizada via Jackson2JsonMessageConverter.
  • Documentação Arquitetural: Elaboração de diagramas descritivos de topologia de mensageria e fluxos de eventos em formato de sequência.

6. Etapa 5: Operação em Produção com Docker, Kubernetes e CI/CD

A etapa final preparou o ecossistema para execução em ambiente produtivo escalável:

  • Conteinerização Multi-Stage Docker: Dockerfiles mínimos baseados em Alpine Linux (JDK 21 builder para JRE 21 runtime nos backends e Bun builder para Nginx nos frontends). Execução segura com usuário não-root (appuser) e verificações nativas de saúde (HEALTHCHECK).
  • Orquestração com Kubernetes: Manifestos completos no namespace isolado taskmanager-prod, contemplando ConfigMaps, Secrets, Deployments com atualização progressiva RollingUpdate (zero indisponibilidade), Services (ClusterIP e NodePort) e Ingress.
  • Escalabilidade Automática (HPA): Configuração de Horizontal Pod Autoscalers para ambos os microsserviços com escala automática de 2 a 10 réplicas quando a utilização média de CPU ultrapassa 70%.
  • Observabilidade Tridimensional:
    • Probes Kubernetes: Spring Boot Actuator configurado com endpoints de liveness (/actuator/health/liveness) e readiness (/actuator/health/readiness).
    • Métricas Abertas: Endpoint /actuator/prometheus raspado periodicamente pelo servidor Prometheus (porta 9090).
    • Rastreamento Distribuído: Instrumentação com Micrometer Tracing Brave e OpenZipkin (porta 9411), propagando traceId e spanId entre requisições HTTP e mensagens AMQP do RabbitMQ, correlacionados nos logs das aplicações.
  • Automação CI/CD com GitHub Actions: Pipeline completo em .github/workflows/ci-cd-tp5.yml executando testes em matriz paralela, validação de lint, build das imagens Docker e validação de schemas Kubernetes com kubeconform e cluster simulado Kind.
  • Testes Abrangentes e Repositório Git: Cobertura de testes unitários, testes de mensageria e testes de integração de observabilidade (ActuatorObservabilityIntegrationTest) com 100% de sucesso. Todo o código versionado no Git com controle criterioso de .gitignore.

8. Conclusão Final

O Projeto de Bloco de Engenharia de Softwares Escaláveis cumpriu integralmente a sua proposta pedagógica e técnica. A evolução progressiva demonstrou como uma aplicação real pode partir de um monólito inicial e, por meio de refatorações fundamentadas em Domain-Driven Design, desacoplamento assíncrono com mensageria e práticas de engenharia de confiabilidade (SRE/DevOps), transformar-se em um sistema distribuído de alto desempenho, tolerante a falhas, observável e preparado para escalonamento automático em ambientes corporativos de produção.
